# Job 锁、进度与渲染负载可观测性执行计划

日期：2026-07-28
状态：已确认，待实施
验证分工：用户负责 QA；本轮执行者仅做静态自检，不运行自动测试、类型检查、构建或浏览器验收。

## 原始计划（已确认，保持不改写）

1. 前端采用 fail-closed 的 job ownership/lock：任务存在、所有权无法确认或锁状态不明确时，禁止可能改变当前项目的操作。由 Workbench 统一传递禁用状态；歌词保存也必须遵守 busy 状态；开始操作须接受这一语义。
2. CLI 与 Web 使用一致的渲染进度语义：TTY 单行刷新，非 TTY 输出稳定阶段并节流；still 有稳定 label；Web 连续 progress 只展示最新值，但语义日志必须保留；支持颜色与 `NO_COLOR`。
3. 输出渲染负载的实际有效配置：draft、宽高、fps、frames、concurrency，并保留旧 `:3000` 服务的现场证据。没有证据不调整默认并发；版本不匹配检测若无法以最小改动实现，列为后续事项。
4. 视频与静态作品的操作文案统一为“调整参数后再渲染/导出”，并展开对应设置。

## 目标与非目标

目标是在不放宽既有项目路径、素材写入、任务取消及扫描身份安全边界的前提下，消除同项目任务的前端并发入口，令命令行与 Web 可观察且语义一致，并让渲染的真实负载参数可被诊断。

明确非目标：本计划不把服务端当前单实例 `409` 行为改成跨进程锁；不凭直觉调整渲染并发；不为 yt-dlp 的进度输出顺带做大范围流式重构；不运行自动化验证或提交。

## 执行批次

### 批次 A：前端 fail-closed job ownership/lock

- 明确 job ownership/lock 状态模型：当前项目存在任务、任务归属无法确认、锁状态未知时均视为 busy，禁用会改变项目或触发竞争任务的入口；只有明确确认可操作时才解锁。
- 在 `Workbench` 形成单一的 busy/lock 来源并向子面板传递，避免各入口自行猜测任务状态。
- 统一禁用开始、素材变更及其他受任务互斥约束的交互；开始请求接受“fail-closed，无法确认即不可开始”的产品语义，保留可读原因和现有取消/进度入口。
- 将 `Materials` 的歌词保存纳入 busy 约束：保存按钮和相关提交路径在 busy 时不能写入，避免其成为绕过锁的入口。
- 保持服务端已有“单实例冲突返回 `409`”的边界；跨进程/跨服务实例的持久锁另立后续决策，绝不混入本批次。

候选影响文件（以实现前静态核对为准）：

- `web/src/Workbench.tsx`
- `web/src/Materials.tsx`
- `web/src/Make.tsx`
- `web/src/useJob.ts`
- `web/src/App.tsx`（仅在 busy 状态须跨层传递时）
- 与上述组件对应的既有测试文件（只更新，不由本轮执行者运行）

验收口径：任务归属或锁状态不能明确确认时，所有受互斥保护的前端入口不可用；任务进度与取消能力仍可见；歌词保存不能在 busy 状态落盘；后端 `409` 仍作为最终防线而非被前端替代。

### 批次 B：统一 CLI/Web 进度契约

- 定义稳定的阶段、label、开始/完成/失败语义，并让视频和 still 都有可预测的阶段标签；still 不得沿用含混或瞬态的文案。
- CLI 在 TTY 使用单行可覆写进度；非 TTY 只输出稳定阶段和节流后的进度更新，保证日志可解析、不会按帧刷屏。
- Web 对连续 progress 更新只保留并渲染最新快照，避免 UI 队列堆积；同时保留语义事件日志，确保阶段转换、完成和失败不因合并最新值而丢失。
- 将颜色输出与 `NO_COLOR` 的行为统一到 CLI 进度输出，确保重定向/CI 输出没有终端控制符或不稳定格式。
- yt-dlp：先确认现有 API 是否可提供足够的稳定阶段进度。若必须把独立调用改为流式读取 stdout/stderr，拆为独立子批次，注明其会影响子进程生命周期、错误聚合、取消和缓冲边界，不与本批次一并重构。

## 依赖、风险与控制

- 前端 fail-closed 必须保留服务端授权与 `409` 防线，不能把 UI 禁用当作安全保证。
- ownership/lock 的初始化与刷新窗口可能误判 busy；宁可暂时禁用并显示原因，也不可开放可能竞争的写入或启动操作。
- 高频 progress 若直接逐事件 setState，可能造成 Web UI 滞后；仅合并展示快照，不得吞掉阶段、错误、取消、完成等语义事件。
- TTY 与非 TTY 的格式判断必须集中，避免各渲染器输出相互矛盾或向日志注入 ANSI 控制序列。
- yt-dlp 的流式重构会改变错误处理与取消时机，必须独立评审、实施、验证和发布。
- 有效 render 配置须在最终默认值、草稿覆盖和并发计算后取得，避免日志给出误导性的请求值。
- 旧 `:3000` 可能是陈旧构建；先采证再解释，不能以其现象推断源代码缺陷或未经测量地改并发。
- 文案展开操作不得重置跨 Tab 音频、未提交参数或正在显示的任务状态。

## 实施记录

状态：实施完成，QA 待用户执行。以下记录追加实施结果，不重写上方“原始计划”或 A–D 批次内容。

### 批次 A 实施：fail-closed job ownership/lock

- 已落实 fail-closed 前端锁：probe 尚未确认、所有权不明、路径不一致或任务仍处于受保护状态时，相关项目写入和新任务入口保持不可用。
- probe 使用 `AbortController`、generation 序号和 path guard：新一轮探测会取消旧请求；旧响应即使随后返回也不能覆盖当前路径或最新 generation 的状态。
- 将锁释放与终态展示分离：任务已完成、失败或取消后，终态信息继续可见；解锁不再依赖于清空终态展示，避免“恢复可操作”与“丢失结果/错误”绑在一起。
- job 状态显式区分 `pending kind` 与 `owned`，让创建中的任务类型、已归属的活动任务及未知归属不再被一个笼统 busy 布尔值混淆。

### 批次 B 实施：CLI/Web 进度契约

#### B1：渲染进度

- CLI 与 Web 均改为消费最新 progress 快照；Web 不再累积连续 progress 更新，同时保留阶段、完成、失败和取消等语义事件。
- 阶段输出采用 stable stage，视频与静态渲染均有稳定可识别的 label；TTY 单行更新与非 TTY 节流输出维持同一阶段语义。
- 已统一语义色的表达边界，使成功、进行、警告/失败等状态在支持颜色时可读，在不支持颜色的场景仍保留文字语义。

#### B2：yt-dlp

- yt-dlp 的进度输出已收口为统一的流式读取与阶段事件路径，并遵守 `NO_COLOR`。
- 未改动 Python 的 fd3 机制；本批次不把该独立输出通道扩展到 Python 侧，避免扩大进程协议、缓冲和取消边界。

### 批次 C 实施：渲染负载可观测性

- 视频 render 输出实际有效 settings：`draft`、宽高、fps、frames 与 concurrency；静态 still 仅输出实际有效的像素、scale、张数与目标。
- Web 和 CLI 走同一份有效配置/诊断链路，避免 Web 展示请求参数、CLI 展示默认参数而彼此不一致。
- 未调整默认并发；没有同环境、同素材的性能证据时，保持当前并发取舍。
- 已记录旧 `localhost:3000` 服务现场为 404；该服务不是可用于确认当前实现的有效现场，需要人工重启后再做 Web/服务版本与行为核对。本轮未在代码中加入不可靠的版本不匹配检测。

### 批次 D 实施：操作文案与设置展开

- 视频结果入口改为“调整参数后再渲染”，并展开视频对应设置。

### 静态审查记录

静态审查发现并修复以下 4 项；均为实现内的状态/语义边界问题，不代表已完成运行时验证。

1. **过期 probe 可以覆盖当前项目的锁状态。** 根因是异步响应只按完成时间写入状态，没有把请求和当前路径/探测轮次绑定。修复为 abort 旧请求，并同时以 generation 与 path guard 拒绝过期响应。
2. **任务终态会随解锁一同被清空。** 根因是锁状态与终态展示共用同一清理路径。修复为分离 lock release 与终态展示，使完成、失败、取消信息仍可复核。
3. **创建中的任务类型与已归属任务混淆。** 根因是单一 busy 状态没有描述 pending 请求、任务 kind 和 ownership。修复为显式保留 `pending kind` 与 `owned` 语义，未知状态继续 fail-closed。
4. **render 活动 TTY 进度与 detail 输出会拼行或擦除不完整。** 根因是单行刷新期间，detail 没有先终结当前活动进度行，且后续擦除/换行边界不统一。修复为在输出 detail 前调用 `endLine` 终结活动行，再按统一边界清理或换行，避免进度与 detail 相互覆盖。
